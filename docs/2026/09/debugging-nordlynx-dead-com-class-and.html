Debugging NordLynx: A Dead COM Class and a Self-Feeding Routing Loop

Reinstalled VMware Workstation over an old VMware Player install, and NordLynx - NordVPN’s WireGuard interface - stopped coming up entirely. No adapter, no tunnel, nothing. The client just sat there retrying. Took a proper diagnostic pass to find out it wasn’t actually a VPN problem at all - it was two unrelated local issues stacked on top of each other, and the second one only showed up once the first was fixed.

Execute:

~ # Get-PnpDevice -Class Net | Where-Object {$_.FriendlyName -match ‘VMware|TAP|Nord|WireGuard|OpenVPN’} | Format-List Status,FriendlyName,Problem

Root Cause #1 - A Stale COM Registration:

That command turned up CM_PROB_NEED_CLASS_CONFIG (error 56) on the VMware, TAP and NordLynx adapters. Not a driver crash - the class installer itself couldn’t finish configuring them. Digging into setupapi.dev.log showed repeated post-install timeouts, and NordVPN’s Telio backend was throwing error 4319 trying to bring the tunnel interface up.

The actual fault was in the registry, not in any driver: HKLM\SOFTWARE\Classes\CLSID\{3d09c1ca-...}\InprocServer32 still pointed at vmware-network.dll under the old VMware Player path, which no longer existed after the Workstation install. Every class-configuration step for those adapters routes through that CLSID, so every one of them failed the same way - VMware’s own virtual adapters, the TAP driver, and NordLynx, none of which have anything to do with each other except sharing that broken pointer.

~ # reg.exe export ‘HKLM\SOFTWARE\Classes\CLSID\{3d09c1ca-2bcc-40b7-b9bb-3f3ec143a87b}’ vmware-bridge-com-before.reg /y ~ # Set-Item -LiteralPath $key -Value ‘C:\Program Files (x86)\VMware\VMware Workstation\vmnetbridge.dll’ ~ # Restart-Service NetSetupSvc

Backed up the key first, confirmed the replacement DLL was actually signed before pointing anything at it, then restarted NetSetupSvc to force it to retry the pending class configuration. Eight seconds later, VMnet1, VMnet8, TAP and NordLynx all flipped from problem code 56 to CM_PROB_NONE in the same pass. One broken registry pointer had been quietly blocking every virtual adapter on the box.

Root Cause #2 - Feeding WireGuard Its Own Packets:

The adapter now existed, but the handshake still wouldn’t complete. Pktmon capture showed the UDP/51820 handshake packets arriving back on NordLynx itself instead of going out the physical interface - the tunnel trying to route through itself, which obviously never finishes a handshake.

Turned out Windows was sharing the public Wi-Fi connection to the private one through ICS, which silently flips on IPv4 forwarding on the shared adapter. Combined with WireGuard-NT’s known interaction between forwarding/WeakHostSend and interface selection via IP_PKTINFO - documented in the wireguard-nt TODO - the box ended up routing the tunnel’s own outbound packets back into itself instead of out to the internet.

Confirmed the hypothesis first with a temporary /32 host route straight to the endpoint on the physical adapter - tunnel connected immediately, proving forwarding was the actual cause and not something else. Removed the test route right after, then fixed it properly: disabled forwarding on the shared adapter and turned off the ICS sharing itself, persisted with netsh after the first attempt through Set-NetIPInterface -PolicyStore PersistentStore failed silently on the policy store lookup.

~ # Set-NetIPInterface -InterfaceIndex $a.ifIndex -AddressFamily IPv4 -Forwarding Disabled -PolicyStore ActiveStore

Validating It Wasn’t A Fluke:

One clean connection doesn’t rule out coincidence. Ran three separate connect cycles, each preceded by a confirmed disconnect, each one checking that the HTTPS request used to verify egress was actually bound to the tunnel’s IPv4 address - not just “internet works,” but “internet works specifically through NordLynx.” Connect times: 6.44s, 4.02s, 4.80s. Last cycle independently confirmed exit country BR, São Paulo, and the client reporting protected: true.

Worth noting for anyone reading this as a kill-switch writeup instead of what it actually is: NordVPN’s own kill switch was already disabled in config (InternetKillSwitch:IsEnabled=False), and stayed that way — nothing here touches it. What I did add is app-level: a startup script that checks for an Up adapter, a valid route, and a tunnel-bound HTTPS response before letting anything else launch, with a 10-second window and an independent watchdog that forces a disconnect if validation doesn’t land in time. It’s a local safety net for my own launch sequence, not a replacement for the client’s kill switch.

What this actually was: Not a VPN bug. Not a driver bug either, really - a stale registry pointer left over from switching VMware editions, plus a Windows feature (ICS) doing exactly what it’s designed to do in a context that broke WireGuard’s routing assumptions. Two unrelated things, same symptom.

What I didn’t touch: No generic network reset, no removing physical adapters, no reinstalling the VPN client, no permanent DNS or firewall changes. Firewall profiles and BFE stayed untouched throughout. Every registry key and interface state I changed got exported first - vmware-bridge-com-before.reg, ics-sharing-before.xml, the interface XML dumps - specifically so this is reversible if something regresses.

What’s still open: VMware’s bridged networking component is registered but vmnetbridge.sys is missing from the drivers folder, so bridged mode itself is still broken - separate from the COM fix, which only restored the configuration path, not the driver. Didn’t chase that one down this time; NAT mode covers what I need for now.
